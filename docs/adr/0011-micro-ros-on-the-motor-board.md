# 11. micro-ROS on the mobile base board

Date: 2026-11-07

Status: accepted. Supersedes in part [ADR 0010](0010-pico-ros-on-the-motor-board.md):
its choice of Pico-ROS. The link, the entities, the motor cut-off and the restart
it describes stand.

## Context

ADR 0010 put Pico-ROS on the mobile base board because, of the two conditions
[ADR 0007](0007-zenoh-middleware-and-mcu-link.md) set for reconsidering micro-ROS,
only the first was met: `micro_ros_setup` had a `lyrical` branch, but
`rmw_zenoh_pico` targeted neither the RP2040 nor Zenoh 1.8 or later.

The second condition is now met, by forks. A fork of `rmw_zenoh_pico` builds for
Lyrical on `zenoh-pico` 1.10.1 and runs on the RP2040, over the same Ethernet over
USB as ADR 0010. 1.10.1 is the Zenoh version that every current branch of
`rmw_zenoh` bundles, and it works with the Zenoh 1.8.0 router of the released
`rmw_zenoh_cpp`. The application is ordinary `rclc` code with no agent:
`rmw_zenoh_pico` replaces `rmw_microxrcedds` under `rcl`, and the board appears in
the graph like any node, as with Pico-ROS.

Getting there took fixes on top of the Lyrical port, carried as patch series in the
forks:

* `rmw_zenoh_pico` cleared its session after creating the session's mutex, and never
  initialised a service's mutex. Both are harmless on Linux, where a zeroed mutex
  is valid, and are hard faults on FreeRTOS: at start and at the first service call.
* It overwrote the key that `zenoh-pico` 1.10.1 copies into each query, leaking
  about 130 bytes per service request until the heap ran out.
* A triggered guard condition did not wake the executor, a detached one stayed
  triggered, and `rmw_wait()` slept through a condition triggered while it was
  checking. Its timeout is also rounded down to whole FreeRTOS ticks, so an `rcl`
  timer made the executor poll.
* It forced `-O0` and traced every function entry.
* It did not implement transient local durability. It now declares the advanced
  publisher `rmw_zenoh_cpp` declares, so late joiners receive the cached samples.
* `zenoh-pico` 1.10.1 still had the two bugs ADR 0010 lists for 1.8.0: the
  batch decoding and the query reply lock.

Both stacks were then measured on the same board, link, host and application;
[HARP3_uC's comparison](https://github.com/robotcopper/HARP3_uC/blob/main/docs/picoros_vs_microros/README.md)
gives the method and the raw results. At 200 MHz, with a 99 Hz command stream:

| Quantity | Pico-ROS | micro-ROS |
| --- | --- | --- |
| Idle time | 82.0 % | 80.0 % |
| Commands down + odometry up, median | 3.88 ms | 3.92 ms |
| Command arrival spread within one second | 0.61 ms | 1.04 ms |
| Service round trip, median / maximum | 2.88 / 4.30 ms | 2.90 / 7.76 ms |
| Late joiner on a transient local topic | 3.3 to 5.3 ms | 3.2 to 3.6 ms |
| Flash | 260 KB | 369 KB |
| RAM left | about 120 KB | about 37 KB |

At the RP2040's default 125 MHz, Pico-ROS is ahead by 1.5 points of idle time and
0.3 to 0.4 ms. The tails differ for a structural reason: Pico-ROS runs callbacks in
the `zenoh-pico` task as samples arrive, and micro-ROS runs them in its executor,
one after the other.

## Decision

The mobile base board's firmware is written with `rclc` and `rcl`, and runs
micro-ROS over `rmw_zenoh_pico` and `zenoh-pico` 1.10.1, at 200 MHz. The firmware
stays in its own repository, HARP3_uC, which pins both forks as submodules.

Everything else in ADR 0010 holds: Ethernet over USB, the addresses, the router's
default configuration, SNTP from `chrony`, `picotool`, the entity table, the 200 ms
motor cut-off and the restart when the session ends.

The micro-ROS agent stays excluded, for ADR 0007's reason. ADR 0007 still governs
every other board.

## Consequences

The firmware uses the standard micro-ROS API. Its message types are generated by
`rosidl` from the `.msg` files of `harp3_msgs`, so the firmware's micro-ROS
workspace includes `harp3_msgs`. Changing a field still means regenerating and
reflashing, as under ADR 0010.

Two forks have to be maintained until their fixes are merged upstream, and
upstream `rmw_zenoh_pico` merges slowly. A `zenoh-pico` or `rmw_zenoh_pico`
upgrade means rebasing the patch series.

The executor runs callbacks one at a time, so the firmware keeps them short and
does not use `rcl` timers. Periodic work is a FreeRTOS task that triggers a guard
condition. A long callback delays every command behind it; the 200 ms cut-off
bounds the consequence, not the delay.

Memory is tighter: 110 KB more flash, and about 37 KB of RAM left against 120 KB,
19 KB of which go to code that runs from RAM to save CPU. In the comparison's
firmware, `zenoh-pico`'s task kept 1152 of its 4096 bytes of stack. The mobile
base firmware must be checked again, since a stack overflow restarts the board.

Until the mobile base firmware is ported, the board runs Pico-ROS as ADR 0010
describes, and ADR 0010's figures describe it.

The comparison also found a limit that applies to both stacks. Between runs, the
board's SNTP offset was several milliseconds off. The odometry stamps the EKF in
`harp3_navigation` receives can therefore be a few milliseconds off the host's
clock, not the 0.1 ms that ADR 0010's clock steps suggest.
